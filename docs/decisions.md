# Decisions and trade-offs
**ADR-12 Dependency-aware partial import (2026-11-04).** At the user's request, restore the original engine's HSDS-object isolation instead of rejecting an entire NDP organization because one address is incomplete. Quarantine each invalid object and all dependent children; store the valid independent graph, conflict requests and held-object evidence in one transaction. Unmappable sources/failed writes remain whole-record quarantine. Keep raw bytes, object reasons, source-record balance and a separate mapped-object balance; show partially accepted records in the admin UI. Official validation and maintenance evaluation thresholds are unchanged.
**ADR-11 Integration repairs and synchronized specifications (2026-11-04).** The user authorized retaining the original engine's official HSDS schemas, core transforms and transaction protections while repairing FINAL's migrations, login and jobs. The shared-file freeze in ADR-9 describes that earlier PR and does not constrain this authorized integration. Keep each affected Kiro design/requirement/task and docs page synchronized. Use uv/uv.lock. Deploy only from alina-cheng/resource_engine; never publish local_refs or the original repository. Workshop Studio credentials and resource lifetime require an explicit temporary-account path; production OIDC is a separate durable-account path. See `kiro-and-prompts-audit.md` and `workshop-aws.md` for the audited baseline and verification state.
**ADR-1 Flask, not FastAPI.** The build environment could not install FastAPI, SQLAlchemy or pytest, so Flask and stdlib SQLite were used to keep everything testable. One Degree prefers FastAPI; routes are thin and the logic is framework-free, so porting is mechanical.
**ADR-2 HSDS as documents inside a relational database.** HSDS is relational on paper but exchanged as nested JSON. Documents keep HSDS version changes cheap (no table migrations); relational tables handle workflow, joins and integrity. DynamoDB was considered and deferred: the data has many-to-many links (a phone can belong to a service, organization and location), flexible filters, and approvals needing transactions. A DynamoDB read model can be generated from the database later if API read volume demands it.
**ADR-3 In-process search by default.** Cheaper and simpler than a cluster at this scale; behind an interface so OpenSearch can replace it. Semantic (embedding) search is not implemented; query expansion approximates it.
**ADR-4 Facts, not wording.** The maintenance worker compares phones, counties, languages, hours and eligibility facts. An extra phone number on an organization's page is ignored unless none of the record's numbers appear.
**ADR-5 Reconcile by field with a source snapshot.** Enough to tell a source update from a human or AI change (R4.2) and to surface clashes (R4.3) without a global rule.
**ADR-6 Jobs as one-off Fargate tasks.** No always-on worker; the same image runs web and jobs.
**ADR-7 No NAT gateway.** Saves a fixed monthly cost; tasks in public subnets are reachable only via the ALB security group. Move tasks to private subnets with NAT or VPC endpoints if policy requires.
**ADR-8 Explicit consent before any request.** The chat never sends a request or shares personal data without a confirm action and a sharing setting.

**ADR-9 AI maintenance detection engine ported from the One Degree monorepo.** The detection engine (fact extractor with verbatim-quote grounding, structured-fact comparator, category precedence and triage, review-need hashing) was ported verbatim into `app/maintenance/` from `onedegree_resource_engine`. It replaces the former inline rule comparison in `MaintenanceService`. The engine is framework-free (depends only on `app.maintenance` and `app.hsds.ids`) and reaches the rest of the app through three ports -- a website source, an HSDS record reader, and a findings sink -- all implemented in `app/services/maintenance_bridge.py`.
  - *Shared-file freeze.* The port required no change to the shared surfaces: `app/container.py` (the `MaintenanceService(...)` constructor is unchanged), `app/db.py` (review-need hashing reuses the existing `check_result.page_hash` / `record_version` columns -- no schema change), `app/config.py` (the extractor reads its own `BEDROCK_MODEL_ID` / `AWS_REGION` / `RE_MODEL_TEMPERATURE`), `app/services/store.py`, `app/services/proposals.py`, `app/web/*`, and `app/hsds/*`. The change-request (`ai_finding`) + `check_result` write contract is preserved, so the API, UI and existing tests are unchanged.
  - *Offline path.* When the LLM is a mock (demo, tests), the deterministic `RuleExtractor` supplies facts to the ported comparator, so no model call is made. The grounded Bedrock extractor runs only when `LLM_BACKEND=bedrock`.
  - *Bridge tuning to resource-engine data.* Two faithful tunings reconcile the engine (built against one-service-per-page seed data) with resource-engine's org-level pages and structured records: phones are confirmed when any stored number appears on the page (ADR-4), and a county named structurally in `service_areas` (`extent_type == "county"`) is surfaced to the engine's text-based county parser. When a page names counties a record lacks entirely, it is reported (missing information or discrepancy) rather than skipped.
**ADR-10 User-report-triggered rechecks: one report, one flag, forced recheck.** Any signed-in user can report a listing that looks wrong (`POST /api/reports`). A single report forces a fresh AI maintenance check of that record on the next run (bypassing the page-unchanged skip) and raises one `user_reported` flag for a specialist, regardless of what the check finds -- detection only proposes, a person decides. We deliberately simplified the source engine's two-flag / distinct-reporter-threshold / cooldown model down to "any report means a human should look": it is easier to reason about and matches the review workflow. Report logic is maintenance-owned (`app/maintenance/reports.py`, wired through `MaintenanceService`); the only shared surfaces are additive -- a `user_report` table and a `flags` column on `check_result` in `app/db.py`, and `POST /api/reports` + `GET /admin/reports` + a resolve endpoint in `app/web/routes_app.py`. Admins see open reports in the console (Reports tab); demo data seeds a few.
