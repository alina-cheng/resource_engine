# Design: AI maintenance worker

- **Detection engine** `app/maintenance/` (ported from the One Degree monorepo, see `docs/decisions.md` ADR-9): `extractor.py` (rule + grounded Bedrock fact extraction with verbatim-quote anti-hallucination), `comparator.py` (structured-fact comparison, category precedence, triage), `worker.py` (review-need hashing), `findings.py` (Finding/Evidence/Category + `finding_problems`). Framework-free; depends only on `app.maintenance` + `app.hsds.ids`.
- `app/services/website.py` source interface: sample (default) and live (user agent, robots.txt, per-host rate limit).
- `app/services/extract.py` rule extractor (offline fact source feeding the ported comparator when the LLM is a mock).
- `app/services/maintenance_bridge.py` implements the engine's three ports (website source, HSDS record reader via `app/hsds/nest`, findings sink) over resource-engine services; translates engine findings into `ai_finding` change requests with **structured, schema-valid HSDS patches** (phones/service_areas/languages/ages/status). Status closures keep their exact HSDS enum value (`defunct` / `temporarily closed`), not a downgraded `inactive`.
- `app/services/maintenance.py` drives the engine; `check_result` stores latest result, page hash, record version and review `flags`.
- **User reports** `app/maintenance/reports.py` (`ReportService`): `user_report` table; a report **selects** the record for the next run and raises the single `user_reported` flag for human review. It respects the hash-skip — the AI re-reviews only if the page changed since the last review; the flag is raised regardless. Endpoints `POST /api/reports`, `GET /admin/reports`, resolve, in `app/web/routes_app.py`; admin "Reports" view + flag badge on records in `frontend/admin.js`.
- **Self-sizing schedule**: `MaintenanceService.daily_batch()` computes checks per run from the live source count: `ceil(active_services / MAINTENANCE_RECHECK_DAYS) * MAINTENANCE_SAFETY_FACTOR`, capped by `MAINTENANCE_MAX_BATCH` (0 = uncapped). `run()` uses it when no explicit `limit` is given. Config in `app/config.py`; Terraform (`infra/terraform`) passes the window/factor/ceiling via the task env and the schedule no longer hard-codes `--limit`. A single daily Fargate task processes the batch sequentially today; sharding across parallel tasks is the planned next step for high volume (decision 1b).
- Scheduling: EventBridge Scheduler runs `python -m app.jobs.run maintenance` (no `--limit`; the run self-sizes).

See `docs/decisions.md` (ADR-9 port, ADR-10 report-trigger, ADR-11 self-sizing schedule), `docs/detailed-design.md` for diagrams and `docs/technical-spec.md` for algorithms.
